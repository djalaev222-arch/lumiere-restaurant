# Lumière — сайт ресторана

SPA-сайт ресторана (React + Vite, JavaScript/JSX) с реальным backend API и админ-панелью: меню, бронирование стола, доставка и настройки ресторана хранятся в базе данных. Анимации на Framer Motion, переключение RU/EN.

**Деплой на бесплатный хостинг (Render, одной кнопкой через `render.yaml`) — см. [DEPLOY.md](./DEPLOY.md).**

## Стек

**Frontend**
- **React 19** + **Vite** — сборка и дев-сервер
- **React Router** — публичные страницы (`/`, `/menu`, `/booking`, `/delivery`, `/about`, `/contacts`) и админка (`/admin/*`) в одном приложении, разными layout'ами
- **Zustand** — корзина доставки (`persist` в `localStorage`), кэш меню и настроек ресторана, загруженных с API
- **React Hook Form + Yup** — валидация форм на клиенте
- **react-i18next** — мультиязычность RU/EN (`src/i18n/locales`)
- **Framer Motion** — анимации секций, переходы между страницами, мобильное меню
- **react-helmet-async** — SEO-теги на каждой странице

**Backend** (`server/`)
- **Express** — REST API: публичное (`/api/menu`, `/api/bookings`, `/api/orders`, `/api/settings`) и админское (`/api/admin/*`, `/api/auth/*`)
- **Prisma + SQLite** — БД (Category, Dish, Booking, Order, OrderItem, Staff, RestaurantSettings); `DATABASE_URL` в `.env` легко переключить на PostgreSQL для продакшена
- **Zod** — серверная валидация везде; цена заказа и стоимость доставки всегда пересчитываются на сервере по актуальным данным из БД (клиенту не доверяем)
- **JWT в httpOnly-cookie** — сессия админки недоступна из JS (защита от кражи через XSS); `express-rate-limit` — на логин и на публичные формы
- Honeypot-поле `company` в бронировании: если бот его заполнил, сервер отвечает "успехом", но запись не создаёт
- Роли персонала: **ADMIN**/**MANAGER** — полный доступ (меню, настройки, брони, заказы); **OPERATOR** — только брони и заказы
- **ЮKassa** — онлайн-оплата заказов доставки (см. раздел ниже)
- **E-mail (Nodemailer) + Telegram-бот** — уведомления о бронях и заказах (см. раздел ниже)

## Запуск (два процесса: API + фронтенд)

```bash
# 1. Backend
cd server
npm install
cp .env.example .env      # сгенерируйте свой JWT_SECRET вместо примера
npm run prisma:migrate     # создаёт dev.db и таблицы
npm run prisma:seed        # заполняет меню (21 блюдо, 5 категорий) + админ-аккаунт
npm run dev                 # API на http://127.0.0.1:4310

# 2. Frontend (в отдельном терминале, из корня проекта)
cp .env.example .env        # VITE_API_URL уже указывает на localhost:4310
npm install
npm run dev                  # сайт на http://127.0.0.1:5199
```

`npm run build` / `npm run preview` — прод-сборка фронтенда, как обычно у Vite.

### Вход в админку

`http://127.0.0.1:5199/admin/login` — логин выводится в консоль после `npm run prisma:seed`:
`admin@lumiere-restaurant.ru` / `change-me-now` (или значение `ADMIN_PASSWORD`, если задали переменную окружения). **Смените пароль перед реальным использованием** — сидируется только для разработки.

### Онлайн-оплата (ЮKassa)

Работает в двух режимах, переключается наличием `YOOKASSA_SHOP_ID`/`YOOKASSA_SECRET_KEY` в `server/.env`:

- **Без ключей (по умолчанию)** — заказ с оплатой "онлайн" принимается сразу же, как демо, без реального списания. Так и есть сейчас, потому что у меня нет ваших реальных мерчант-данных ЮKassa.
- **С ключами** — при оформлении заказа сервер создаёт платёж в ЮKassa и возвращает ссылку на их платёжную страницу, куда браузер клиента редиректится. После оплаты ЮKassa возвращает клиента на `/delivery/payment-result`, а статус подтверждается через вебхук `POST /api/payments/yookassa/webhook` (сервер сам перепроверяет платёж по их API, не доверяя телу вебхука напрямую — иначе его можно подделать).

Чтобы включить: зарегистрируйтесь на [yookassa.ru/developers](https://yookassa.ru/developers/using-api/testing) (тестовый режим не требует юрлица), впишите `shopId`/`secretKey` в `.env`, и в личном кабинете ЮKassa укажите адрес вебхука — `https://ваш-домен/api/payments/yookassa/webhook` (для локальной разработки нужен туннель вроде ngrok, т.к. ЮKassa должна достучаться до вашего сервера снаружи).

Цена и статус оплаты полностью на сервере — клиент не может подделать сумму или отметить заказ оплаченным.

### Уведомления (e-mail + Telegram)

Как и оплата, работает в двух режимах — без настройки ничего не ломается, просто пишет в консоль сервера вместо реальной отправки:

- **Клиенту (e-mail)** — подтверждение при создании брони/заказа (если указан e-mail — поле необязательное и в форме брони, и в форме заказа) и уведомление при каждой смене статуса из админки (бронь подтверждена/отклонена/перенесена; заказ готовится/в пути/доставлен/отменён).
- **Ресторану (Telegram)** — сообщение в чат при каждой новой брони и новом заказе, с именем, телефоном, составом и суммой.

Включается независимо друг от друга:
- **E-mail** — впишите `SMTP_HOST`/`SMTP_USER`/`SMTP_PASS` в `server/.env` (подходит любой провайдер: Yandex, Gmail с app password, Mailgun и т.д.)
- **Telegram** — создайте бота через [@BotFather](https://t.me/BotFather) (минута, бесплатно), напишите ему один раз, откройте `https://api.telegram.org/bot<TOKEN>/getUpdates`, чтобы найти свой `chat_id`, впишите оба значения в `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`

Уведомления отправляются в фоне и никогда не блокируют и не ломают создание брони/заказа, даже если SMTP или Telegram недоступны.

SMS не реализованы — требуют платного шлюза (SMS.ru, Twilio и т.п.) с привязкой номера отправителя, что нельзя настроить без ваших данных; e-mail и Telegram покрывают те же сценарии без этой зависимости.

## Тесты

**Backend — интеграционные тесты API** (Vitest + Supertest, отдельная `test.db`, создаётся и удаляется автоматически):

```bash
cd server
npm test
```

27 тестов покрывают самое важное: пересчёт цены на сервере (клиентскую цену игнорирует), honeypot в бронировании, ролевой доступ (OPERATOR не может редактировать меню), httpOnly-сессия (логин/логаут/защищённые роуты), валидацию (телефон, прошедшая дата, лимит гостей), запрет удаления блюда с историей заказов.

**Frontend — E2E** (Playwright, из корня проекта):

```bash
npm run test:e2e
```

14 тестов гоняют реальный браузер по сайту и админке: меню (фильтры, поиск), бронирование (валидация + успех), доставка (корзина, чекаут), админка (редирект неавторизованных, логин/логаут). По умолчанию переиспользует уже запущенные `npm run dev` — если их нет, поднимет сам. **Важно:** тесты пишут реальные брони/заказы/блюда в `dev.db` — после прогона стоит сделать `npm run prisma:seed` в `server/`, чтобы вернуть чистое состояние (я это уже сделал).

## Структура

- `src/data/menu.js` — источник данных для сидирования БД (`server/prisma/seed.js` его импортирует); фронтенд меню больше не читает
- `src/hooks/useMenu.js`, `useSettings.js` + `src/store/menuStore.js`, `settingsStore.js` — загрузка и кэш данных с публичного API
- `src/lib/api.js` — клиент для публичных запросов; `src/lib/adminApi.js` — клиент для админки (с cookie-сессией)
- `src/store/cartStore.js` — состояние корзины; `src/store/adminAuthStore.js` — состояние сессии персонала (сам токен в JS не хранится)
- `src/pages/admin/`, `src/components/admin/` — админ-панель (дашборд, брони, заказы, меню, настройки)
- `server/src/routes|controllers|validators` — REST API; `server/src/routes/admin/` — защищённые маршруты
- `server/prisma/schema.prisma` — схема БД
- `server/tests/` — интеграционные тесты API; `e2e/` (в корне) — E2E-тесты фронтенда и админки

## Что реализовано как заглушка (MVP)

- **Онлайн-оплата** — код интеграции с ЮKassa готов и рабочий (см. выше), но без реальных ключей магазина работает в демо-режиме.
- **Уведомления** — e-mail и Telegram готовы и рабочие (см. выше), но без SMTP/Telegram-креденшлов только логируются в консоль. SMS не реализованы вовсе.
- **Карта** — OpenStreetMap embed без API-ключа; для продакшена можно заменить на Яндекс.Карты/Google Maps.
- **Перенос брони** — в статусах брони есть RESCHEDULED, но нет отдельного UI для выбора новой даты/времени — это просто пометка.
